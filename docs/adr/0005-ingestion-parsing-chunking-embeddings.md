# ADR-0005: Ingestion: pinned corpus, 10-K parsing, token-aware chunking, Gemini embeddings

- **Status:** Accepted
- **Date:** 2026-10-02

## Context
Retrieval quality depends on what is indexed: clean text, meaningful section labels, chunks the
embedding model accepts, and vectors that rank the same way in both vector stores. The
evaluation golden set (Phase 5) also needs a corpus that never silently changes.

## Decisions

### Corpus: the latest 10-K per company, pinned by accession number
- `ingest/corpus.toml` lists each filing: ticker, CIK, accession, period end, filed date. It's
  generated by `python -m ingest.corpus resolve` and committed.
- New SEC filings never change the corpus underneath the golden set.
- **CIKs are pinned explicitly.** Tickers can move between legal entities: `XOM` now maps to a new
  "ExxonMobil Holdings Corp" with no 10-K. The FY2025 10-K was filed by CIK 34088.
- **`fiscal_year`** is the year of `period_end`, which matches each issuer's own convention
  (NVDA's FY2026 ends in January 2026).
- **The corpus mixes FY2025 and FY2026:** MSFT, NVDA, PG and WMT have already filed FY2026
  10-Ks. Every chunk carries its own year.

### Parsing: HTML → text → sections by Item
- **Text extraction:**
  - Hidden inline-XBRL facts are dropped.
  - Tables are flattened to `label | value | value`, with `$`, `%` and `( )` cells merged, so
    figures stay next to their labels.
  - Page numbers are removed.
- **Item splitting uses a longest-run rule.** It handles tables of contents, per-page running
  headers (MSFT), and cross-references.
- **Appended financial sections are recovered.** JPM, XOM, CVX, DIS and NVDA put MD&A and
  financial statements *after* Part III/IV, with stubs under Items 7 and 8. Inside an oversized
  late Item, MD&A and financial-statement sub-headings are relabelled Item 7 and Item 8.
- **Verified on all 20 filings:** 100% of text is kept and none is duplicated, and every filing
  has non-trivial Items 1, 1A, 7 and 8.
- **Fallback:** a single unsectioned document when fewer than 6 Items are found, rather than
  guessing.

### Chunking: paragraph-packed, with a character target *and* an estimated-token cap
- **Limits:** 3,000-character target, 1,200 estimated-token cap, 400-character overlap.
  Oversized paragraphs are split on sentences, then hard-wrapped as a last resort.
- **Why the token cap exists:** the first full run failed on GS. A 3,000-character table chunk
  was 2,114 tokens, over the model's 2,048 limit, because the tokenizer splits digits
  individually and chars÷4 underestimates tables by up to 2.9×.
- **Estimator:** digits + 1.3×words + punctuation, calibrated on 1,366 real API token counts.
  The worst case is 1.21× on large chunks.
- **Result:** after the fix, the largest real chunk is 1,454 tokens.
- **Versioning:** bumping `CHUNKER_VERSION` forces re-chunking.

### Contextual chunk header
- Each chunk is embedded as `"<Company> (<TICKER>) Form 10-K, fiscal year <Y> (period ended …).
  Item <N>. <Title>.\n\n<content>"`.
- Without it, "revenue grew 6%" is indistinguishable across 20 companies.
- The stored `content` stays clean; the header is rebuilt from metadata.

### Embeddings: `gemini-embedding-001` at 768 dimensions, L2-normalised by us
- **Model:** it's Google's recommended text-embedding model; it supersedes `text-embedding-005`,
  which is also 768-d but English-only.
- **Dimension:** the full size is 3,072; Matryoshka truncation to 768 keeps the schema and the
  index small.
- **Normalisation:** truncated outputs are **not** unit-length (measured norm ≈ 0.59), so the
  pipeline L2-normalises every vector. That keeps cosine (pgvector) and dot product (Vector
  Search) rankings identical.
- **Task types:** `RETRIEVAL_DOCUMENT` for chunks; queries will use `RETRIEVAL_QUERY`.
- **Truncation:** `auto_truncate=False`, so over-long inputs fail loudly instead of being
  silently cut.
- **Cost logging:** token counts come from the API's per-embedding statistics, so cost logs use
  real numbers. Pricing is $0.15 per 1M input tokens (online), checked 2026-10-02.

### Pipeline mechanics
- **Concurrency:** bounded per boundary.
  - SEC: rate limiter at 5 req/s, under SEC's 10/s limit.
  - Embeddings: semaphore of 4 concurrent requests, batches of ≤ 100 texts and ≤ 15,000
    estimated tokens.
  - Filings in flight: at most 8.
- **Retries:** exponential backoff with jitter on 429/5xx and transport errors. 4xx client
  errors are not retried.
- **Idempotency:**
  - Each document is written in one transaction (upsert the document, replace its chunks).
  - Unchanged filings are skipped by (content SHA-256, chunker version, embedding model).
- **Fault isolation:** a failing filing is reported and skipped; it never aborts the run. The GS
  failure proved this.
- **Run reports:** every run writes `results/ingest/<timestamp>_<mode>.json`, the source for any
  throughput or cost number.

## Consequences
- **The `vector(768)` schema stays.** Changing the model or dimension needs a migration and a
  full re-embed.
- **Parsing heuristics are tuned on these 20 filings.** New issuers should be checked with
  `make ingest-dry` (Item coverage per filing) before embedding.
- **Not done yet:** Vector Search upserts. The index is only reachable inside the VPC
  (ADR-0002), so that sink is added in Phase 4 and runs as a Cloud Run Job.
